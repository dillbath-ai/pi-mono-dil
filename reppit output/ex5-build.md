## Interesting Findings

### 1. MCP SDK export map changed between proposal and SDK 1.29.0

The research proposal assumed sub-path imports like:
```typescript
import { Client } from "@modelcontextprotocol/sdk/client/index.js";
import { StdioClientTransport } from "@modelcontextprotocol/sdk/client/stdio.js";
```

The SDK's actual `package.json` `exports` field does not list those paths explicitly. Instead it uses a wildcard:
```json
{
  "./*": {
    "types": "./dist/esm/*.d.ts",
    "import": "./dist/esm/*",
    "require": "./dist/cjs/*"
  }
}
```

The wildcard means `@modelcontextprotocol/sdk/client/stdio.js` maps to `./dist/esm/client/stdio.js` at runtime — which does exist. The imports work, but the matching logic is `"./client/stdio.js"` → wildcard `*` = `"client/stdio.js"` → `"./dist/esm/client/stdio.js"`. This is correct but non-obvious.

**Named export `./client`** (without the `.js`) maps only `Client` and is separate:
```json
"./client": { "import": "./dist/esm/client/index.js" }
```

### 2. vi.mock() cannot intercept cross-directory module resolution in a monorepo

The MCP SDK is installed in `.pi/extensions/mcp/node_modules/`. When `transport.ts` imports `@modelcontextprotocol/sdk/client/stdio.js`, Node resolves it to an absolute path under `.pi/extensions/mcp/node_modules/...`. 

Vitest runs from `packages/coding-agent/` and registers vi.mock() for `@modelcontextprotocol/sdk/client/stdio.js` — but it resolves that identifier from `packages/coding-agent/`, yielding a different absolute path (or no path at all if not installed there). The mock is never applied to the actual import inside `transport.ts`.

**Consequence**: Unit tests for `createTransport()` that verify constructor call counts don't work. Tests were restructured to verify observable behaviour (return type, throws on invalid config) instead of mock call assertions.

**Workaround options for future consideration**:
- Add MCP SDK as a devDependency in `packages/coding-agent/` (enables vitest to resolve it)
- Use vitest's `server.deps.inline` or `resolve.alias` to point the mock at the extension's local copy
- Run extension tests from within `.pi/extensions/mcp/` with their own vitest setup
- Dependency-inject the client factory into `index.ts` for testability

### 3. `resolveConfigValue()` is not exported from `@mariozechner/pi-coding-agent`

The plan called for using pi's internal `resolveConfigValue()` from `packages/coding-agent/src/core/resolve-config-value.ts`. That function is not in the public package index. It cannot be imported by an extension.

Pi's `resolveConfigValue()` also has different semantics than what the proposal assumed: it reads `process.env[value]` (treating the whole string as an env var name) and supports shell commands via `!` prefix — it does NOT support `${ENV_VAR}` interpolation syntax.

**Decision**: Implemented a self-contained `resolveEnvValue()` in `config.ts` using a simple regex:
```typescript
export function resolveEnvValue(value: string): string {
  return value.replace(/\$\{([^}]+)\}/g, (_, key) => process.env[key] ?? "");
}
```
This is more intuitive for the mcp.json use case, consistent with how Docker Compose and other tools handle env interpolation in config files, and requires no pi internals.

### 4. `promptSnippet` is non-negotiable for LLM discoverability

Confirmed in `agent-session-dynamic-tools.test.ts` line 88:
```typescript
expect(session.systemPrompt).toContain("- dynamic_tool: Run dynamic test behavior");
```
Tools without `promptSnippet` are omitted from the "Available tools" section of the system prompt. The LLM would not call MCP tools if `promptSnippet` is absent — they'd be invisible to it. Every tool registered in `index.ts` sets `promptSnippet: tool.description ?? tool.name`.

### 5. `throw` vs `return` in tool execute() matters for isError flag

Documented in `extensions.md:1725`:
> "Returning a value never sets the error flag regardless of what properties you include."

The validation failure path in `execute()` uses `throw new Error(...)`. If it returned an error message as content instead, `isError` would remain false on the tool result — the LLM would treat the validation failure as a successful tool call.

### 6. Module caching affects factory test isolation

ESM modules are cached on first import. All factory tests share the same `index.ts` module instance. The `clients` Map in `index.ts` is module-level state. Tests that exercise `session_start` followed by `session_shutdown` must account for the fact that a previous test's state may still be in the map.

The current tests avoid this by using an empty-config case or a failing-connect case, neither of which populates `clients`. Integration tests (separate from the unit test suite) are needed to exercise the full happy path.

## Known Gap: Integration Tests

The plan called for integration tests spinning up a real `@modelcontextprotocol/server-filesystem` subprocess. These were not implemented because:
1. The MCP server npm package is not installed in the repo
2. Integration tests require a live pi session, which needs the compiled pi binary or SDK test harness wired to real extensions on disk
3. The cross-directory module resolution issue (finding 2) means extension integration tests can't be run cleanly from the existing vitest setup

**Recommended path**: Run integration tests via `pi -e .pi/extensions/mcp/index.ts -p "list files in /tmp"` after creating a `.pi/mcp.json` pointing to `@modelcontextprotocol/server-filesystem`. The extension will auto-discover from `.pi/extensions/` without any configuration.

## Usage

Create `.pi/mcp.json` in any project:
```json
{
  "servers": [
    {
      "name": "filesystem",
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/tmp"]
    },
    {
      "name": "github",
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_TOKEN": "${GITHUB_TOKEN}" }
    },
    {
      "name": "remote",
      "url": "http://localhost:3000/sse"
    }
  ]
}
```

The extension auto-loads (`.pi/extensions/mcp/` is an auto-discovery path). On session start, pi will notify:
```
MCP: connected filesystem (5 tools)
MCP: connected github (8 tools)
```

Tools appear as `mcp__filesystem__list_directory`, `mcp__github__create_issue`, etc. in the LLM's tool list and are called automatically based on the user's prompt. Use `/mcp` to inspect connected servers at runtime.
